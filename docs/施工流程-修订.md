## 修正 3：热键不要只写旧版 `Input`

PEAK 带了 `Unity.InputSystem.dll`。如果工程的 Active Input Handling 只开新系统，
`UnityEngine.Input.GetKeyDown` 会**运行时抛 `InvalidOperationException`**，不是返回 false。

`AudioProbe.KeyPressed()` 的处理顺序：先读 `UnityEngine.InputSystem.Keyboard.current`，
拿到就用；拿不到或被关掉才回退旧版 `Input`，并把失败原因打进日志。
所以第一次按 F7 如果没反应，看日志里有没有这两行之一——这本身就是需要记录的环境结论。

## 修正 4：`streamAudio = true` 时，请求对象不能 Dispose ★（原文没写，会直接断音）

```
req = UnityWebRequestMultimedia.GetAudioClip(url, AudioType.MPEG);
((DownloadHandlerAudioClip)req.downloadHandler).streamAudio = true;
yield return req.SendWebRequest();
clip = DownloadHandlerAudioClip.GetContent(req);
req.Dispose();          // ← 这一行会让声音当场停掉
```

流式模式下 `clip` 只是"正在下载的这层缓冲"的视图，`Dispose` 把缓冲收走，音频立刻静音。
必须先 `AudioSource.Stop()` + `clip = null`，再 `Dispose` 请求。`AudioProbe` 里
`_activeRequest` 字段就是为此存在的，清理统一走 `StopCoroutineSafeCore()`。

## 修正 7：闸门素材要选"你这台机器真能跑得动"的源，并且别写死 timeout ★（第一次实测打出来的）

第一次实测结果：

```
[探针] 起播失败 [A] code=200 err=Request timeout 耗时=25006ms
```

`code=200` 说明 TCP / TLS / HTTP 全通，问题在下载 body 太慢。实测带宽：

| 目标 | 带宽 | 8.7 MB 需要 |
|---|---|---|
| soundhelix.com | **27.1 KB/s** | **323 秒** |
| 127.0.0.1:8765（本机 HTTP） | 125 MB/s | 0.03 秒 |

两条修正：

1. **闸门素材换成"本机 HTTP 服务 + 本地 mp3"**。它走的是同一套 `UnityWebRequest` 网络栈，
   请求头、连接、解码、播放、seek、清理全都验到，唯一没覆盖的是公网带宽——而公网带宽是
   网易 CDN 的事（国内通常 2–10 MB/s），不是 Unity 的事。工程里 `testmedia\serve.py`
   已经支持 Range（`python -m http.server` 不支持 Range，测出来的行为是假的）。
2. **`timeout` 不要写死**。Unity 的 `timeout` 是整条请求的总时限，慢链路上 25 秒必然失败，
   而错误信息只会告诉你 "Request timeout"，看起来像代码坏了。
   现在它是配置项 `TimeoutSeconds`，默认 `0`（不限）；并且下载期间每帧刷新缓冲百分比、
   每 10% 打一行 `缓冲 xx% xxKB`，屏幕和日志都能看到进度，不再"按了没反应"。

顺带记一个数：PEAK 启动后 `Resources.FindObjectsOfTypeAll<AudioClip>()` 已经是 **379** 个。
但这个 379 只是插件 `Start()` 那一刻的数，进主菜单后游戏会把音频加载到 **660** 个——
判"压测有没有漏"必须用**同一时刻的前后对比**（660 → 660），跨阶段比会得出错误结论。

## 修正 8：阶段 1 闸门已过，实测数字 + 原文没写的三个坑 ★（2026-11-07 21:05）

| 闸门项 | 原文目标 | 实测 | 判定 |
|---|---|---|---|
| 起播延迟 | < 1.5 s | **46 ms**（网络 38 + 解码 8） | ✅ |
| `clip.length` 可信 | > 0 | 237.11 s / 44100 Hz / 2ch / `Loaded` | ✅ |
| seek 到 60 s | 落位且推进 | 60.00 → 62.77 → 63.75 s | ✅ |
| 切歌 20 次 clip 计数 | 不涨 | 660 → 660 | ✅ |
| 退出干净 | 无异常 | `AudioProbe 已销毁，资源已释放` | ✅ |
| 热键走哪套输入 | — | **Input System**（`Keyboard.current`），旧版 `Input` 未参与 | — |

**坑 1：`streamAudio = true` 时 `downloadProgress` / `downloadedBytes` 恒为 0。**
流式模式下请求在"流接上"就完成，进度回调没有数据，日志里每个请求只有一条 `缓冲 0% 0KB`。
→ 阶段 3 的缓冲进度条不能用 `req.downloadProgress`，要么自己写 `DownloadHandlerScript` 数字节，要么放弃流式。

**坑 2：流式下 `AudioSource.time` 不等于墙钟。**
seek 后 1 秒墙钟内 `time` 走了 3.75 秒。落位判定够用，但**做进度条 / 歌词同步会漂**。
→ 要精确进度用 `AudioSettings.dspTime` 自己算差。

**坑 3：本机 125 MB/s 会掩盖"流式是否真生效"。**
3.7 MB 的曲子 30 ms 就下完，"秒开"和"整曲下完再播"表现完全一样，46 ms 证明不了 `streamAudio` 起作用。
→ 探针加了 `F5`：`serve.py 8766 512` 限速 512 KB/s（整曲约 7.2 s），3 秒后往缓冲区间外 seek。
这条结论决定阶段 3 的"从第 N 秒开始播"要不要自己做 Range 重请求，**但不挡阶段 2**。

## 修正 9：阶段 2 的 weapi 加密可以整段跳过；但"登录"不是全有全无 ★（2026-11-07 21:18 实测）

原文 2.1 要求先实现 `AES-128-CBC ×2 + RSA(1024)` 才能调接口。**不需要。** 实测明文 `/api/` 接口匿名就能用：

| 接口 | 明文可用 | 实测 |
|---|---|---|
| `POST /api/cloudsearch/pc`（搜索） | ✅ | `s=雨爱` 返回 8 条，字段含 `fee` / `privilege.st` |
| `GET /api/song/lyric/v1`（歌词） | ✅ | 316100 返回 56 行，含 LRC 时间戳 |
| `POST /api/login/qrcode/unikey`（二维码） | ✅ | `{"code":200,"unikey":"5c5964ba-…"}` |
| `POST /api/song/enhance/player/url/v1`（播放地址） | ⚠️ 看情况 | 见下 |

**播放地址不是"必须登录"，是"看这首歌要不要钱"：**

| 曲目 | fee | 匿名结果 |
|---|---|---|
| 3443155291（DJ 版，免费） | 0 | **拿到 320kbps 直链**，`m801.music.126.net`，206 + `audio/mpeg` + ID3，5,409,480 字节，能播 |
| 316100（杨丞琳《雨爱》） | 1 | `url=null`，`code=-110`（需会员） |

结论：**不登录也能完整跑通"搜索 → 取直链 → 播放"**，只是播放范围限于免费曲目；登录后解锁会员曲库。
这改变阶段 2 的优先级——先把免费的链路跑通，登录作为增强项。

### 直链的时效（必须遵守）

`http://m801.music.126.net/20261107214325/…/xxx.mp3?vuutv=<签名>&cdntag=…`

路径里带**日期时间戳**、查询串带**签名**，这是有时效的临时地址。所以：
- **绝不缓存直链、绝不落盘**；每次用户点播放现取一次（这也正好符合 2.4 的"不预取"）；
- 单曲循环不要重复请求，缓存的是"正在播的这个 AudioClip"，不是 URL。

### 实现里已经处理的细节

1. **`code == -460`（风控）**：退避 5 秒重试一次，再失败就抛"请求过于频繁"，不静默当成空结果。
2. **`freeTrialInfo != null`**：说明只给了试听片段，`SongUrlResult.Explain()` 会明说"必须丢弃"，不会静默播 30 秒。
3. **LRC 里混着 JSON 署名行**（`{"t":0,"c":[{"tx":"作词: "}]}`），标准 LRC 解析器会把它当歌词。`LrcDocument` 已经过滤。
4. **net472 的 SDK 风格工程不会自动带 `System.Net.Http`**，必须显式 `<Reference Include="System.Net.Http" />`，否则 `HttpClient` 报 CS0234/CS0246。
5. **不引 Newtonsoft**：Unity 里塞第二份 Newtonsoft 极易和游戏自带版本打架（表现为 MissingMethodException）。改为自带的 200 行 `MiniJson`。

### 这套东西的位置

```
PeakMusic.Core/
├─ Throttle.cs              串行 + 200–500ms 随机（所有请求必须过它）
├─ Netease/MiniJson.cs      零依赖 JSON 解析
├─ Netease/NeteaseModels.cs SongInfo / SongUrlResult / LyricResult / QrLoginResult
├─ Netease/NeteaseClient.cs 搜索 / 播放地址 / 歌词 / 扫码登录 / 账号
├─ Netease/CookieStore.cs   %APPDATA%\PeakMusic\cookie.txt，只存 MUSIC_U 等 5 项
└─ Lyrics/LrcDocument.cs    LRC 解析 + 按秒二分定位（阶段 3 歌词同步直接用）
```

## 修正 10：阶段 3 的 IMGUI 面板，输入不能靠 `Event.current` ★（2026-11-07 21:52）

原文阶段 3 写的是"F1 打开 IMGUI 面板，输入歌名、回车搜索"，默认 `GUI.Button` / `GUI.TextField` 可用。
但在**只开新输入系统**的构建里，IMGUI 的键盘/鼠标事件并不可靠——而 PEAK 正是这种构建（阶段 1 实测热键全走 `Keyboard.current`）。

正确做法（已在 `MusicPanel.cs` 落地）：

- **画**只用 `GUI.Box` / `GUI.Label`，不碰 `GUI.Button` / `TextField`
- **点**自己读 `Mouse.current.position` + `leftButton.wasPressedThisFrame`，Y 轴翻转成 GUI 坐标（左上原点）
- **打字**订阅 `Keyboard.current.onTextInput`，退格/回车按 `Key.Backspace` / `Key.Enter` 处理
- 布局在 `Update` 与 `OnGUI` 里用**同一个** `ComputeLayout()`，保证命中区域和画出来的一致
- 中文字形必须 `Font.CreateDynamicFontFromOSFont("Microsoft YaHei", 15)`，否则全是方块

另：**原文没提 F1 会跟别的 mod 冲突**。这里 F1 是主键、F2 是备用键，两个都能开关面板。

## 修正 11：`startAt > 0` 的播放不许走流式

阶段 1 的 F5 实测已经证明：`streamAudio = true` 时远距 seek 不落位（目标 222s，1 秒后仍在 0.00s）。
所以"从第 N 秒开始播"只有两条路：整曲下完再 seek，或者自己做 Range 重请求。
`MusicPlayer.Play(song, url, startAt)` 现在在 `startAt > 0.5s` 时强制 `streamAudio = false`。

## 修正 12：砍掉「下雨自动切歌」★（2026-11-07 21:54 用户决定）
原文阶段 3 收尾要求"下雨时自动播放某首歌/自动切歌"。**这一条不做，从范围里删除。**

理由不是技术做不到，而是产品判断：插件的定位改为**纯手动点歌机**——F1 开面板、搜索、点一首、播放，行为完全由玩家操作决定。

连带影响：

- 不 patch 天气状态机，不读 `WeatherManager` 之类的游戏内部状态（这类 patch 是 mod 冲突和版本更新后崩溃的主要来源）
- `startAt`（从第 N 秒起播）**保留在 `MusicPlayer` API 里**，因为暂停恢复、拖进度都要用；但游戏内没有任何自动路径会传非 0 值
- 因此阶段 3 不需要"自己做 Range 重请求"——那是为"雨一落就从第 60 秒接上"准备的，既然不自动起播，这条取舍就不必付

## 修正 13：分页别把"远程 offset"和"本地下标"混成一个变量 ★（2026-11-07 22:06）

实机第一版：面板、搜索、中文、列表全正常，**唯独「上一页/下一页」点了没反应**。

根因不是坐标算错（点击能命中），而是判据自相矛盾：

```csharp
_total = _songs.Count + _page;          // 一次只取 8 首 → _total = 8
if (_page + PageStep + PageSize <= _total) ...   // 20+8 <= 8，永假
else if (_page + PageSize < _total) ...          // 0+8 < 8，永假
```

`PageStep` 是 20，`_total` 却是 8，两个分支永不成立。而且 `_page` 被同时当作
`SearchAsync` 的 `offset` 和 `_songs` 的下标——即便判据修对，第 2 页也会立刻空白（`idx >= Count` 直接 break）。

正确做法（已落地）：

- 搜索**一次取 40 首**（`FetchLimit`），`_page` 只表示本地起始下标（0/8/16/24/32）
- 翻页 `min(_page+PageSize, MaxPageStart)` / `max(0, _page-PageSize)`，`MaxPageStart = ((Count-1)/PageSize)*PageSize`
- **到边界必须给反馈**：状态行打"已经是最后一页（第 3/3 页）"，按钮变灰。
  静默无反应等于让人以为功能坏了——这次的误报就是这么来的
- 加页码「第 x/y 页 · 共 n 首」+ 滚轮翻页（只在鼠标位于列表内响应，避免抢游戏镜头缩放）
- 不做服务端翻页：每翻一页重发搜索，白白提高 `-460` 风控概率；40 首对点歌机够用

同批修掉的另一个空头承诺：底部提示一直写"按 T 输入"，但代码里从未绑定 T。
